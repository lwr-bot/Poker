# 一致性与故障处理

## 三条边界

1. 一张桌只有一个游戏节点拥有。
2. 一个进程内一张桌只有一个逻辑执行器写入。
3. 钱包与已结算历史只有 MySQL 可以确认。

Redis 只保存可过期的协调信息。Redis Pub/Sub 即使后续加入，也只能发送允许丢失的大厅刷新通知。

## 幂等

- 内存重放缓存阻止同一节点内重复业务命令。
- 客户端序号阻止旧命令和跳号命令。
- 钱包账本唯一键阻止服务重启后的重复买入/兑出。
- 手牌主键和动作唯一键阻止重复动作历史与二次结算。
- 同桌持久化栅栏保证动作 N 落库后才允许动作 N+1 进入领域状态机。

TCP 的可靠有序只表示字节到达，不表示业务回调没有重试，因此不能替代这些约束。

## 结算顺序

服务端状态机计算结果后，将动作和结算交给存储线程。动作日志成功落库后才回复快照；结算事务成功后才发布最终结果。存储边界会再次验证用户唯一、牌不重复、投入/赢取/结束筹码等式和总底池守恒，并用开局筹码作为 SQL 更新条件。任一动作日志或结算写入失败都会立即封闭本地桌，拒绝已经排队但尚未执行的旧命令，并进入整桌退款路径，避免内存牌局继续领先于事实数据。

首次退款失败时，客户端收到 `table_aborted_refund_pending` 事件，服务端按 1、2、4、8、16、32 秒的退避序列重试（后续间隔封顶 32 秒），最多八次。成功后产生 `table_refund_completed`；耗尽后产生 `table_refund_requires_reconciliation` 并保留 MySQL 桌上筹码记录，供运维对账。退款事务和 `crash_refund` 账本键均可重复执行，不会二次入账。

## Redis 故障

- 已经在游戏节点中的牌局不依赖 Redis 转发，继续运行。
- 新建桌、查询所属节点和消费加入凭证失败关闭。
- 故障回收器先 `PING` Redis；Redis 本身不可用时不会把所有节点误判为死亡。

## 游戏节点故障

游戏节点每 2 秒写一个 6 秒 TTL。大厅看到所属节点消失后再等待 `POKER_NODE_FAILURE_GRACE_MS`：

1. 停止给该节点分配新桌。
2. 查询仍属于该节点的开放桌。
3. 事务把 `table_seats.stack` 退回钱包并写 `crash_refund` 账本。
4. 删除座位并把桌标记 `aborted`。

版本一不迁移内存牌局，因为两个节点同时接管比中止一手牌更危险。

游戏节点启动时先检查相同 `node_id` 是否仍有健康实例；若有则拒绝启动。确认没有重复实例后，它会把 MySQL 中仍归属于自己的旧开放桌全部中止退款，再开始上报心跳。这样节点在保护窗口内快速重启也不会因复用同一个节点标识而掩盖上一次进程丢失的内存牌局。

## 已知边界

- 开发 Compose 没有 TLS。
- 重放缓存本身不跨进程；金融唯一键承担重启后的最终保护。
- 回收器单次扫描 200 张开放桌，生产规模需要分页与回收任务租约。
- 单次启动恢复最多检查 10,000 张开放桌；更大规模需要按节点分页扫描。
