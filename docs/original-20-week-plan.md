# C++ 实时德州扑克服务器整体计划（长期目标基线）

> 本文保存最初确定的完整项目路线。它描述的是最终目标，不代表当前代码已经完成全部验收。当前实现状态和下一步入口见 [`PROJECT_MEMORY.md`](../PROJECT_MEMORY.md)。

## 1. 项目定位与最终目标

项目定位为：**基于 C++17/Muduo 的分布式实时德州扑克后端**，主要面向 C++ 后端、游戏服务器和部分基础架构校招岗位。

最终交付物：

- 2～6 人无限注德州扑克现金桌，只使用虚拟筹码，不涉及充值或真实货币。
- 支持注册登录、创建/加入房间、入座、准备、盲注、下注、加注、全押、边池、摊牌、平分底池、超时处理、离开和断线重连。
- 服务端权威判定；客户端只能发送操作意图，不能决定牌面、筹码或胜负。
- Ubuntu 部署，提供 Docker Compose、一键构建、自动测试、压测报告、架构文档和演示视频。
- 单实例完整可用后，再扩展为一个大厅节点和两个游戏节点的多实例演示。
- 最终使用 Qt 6 Quick/QML 制作桌面客户端，C++ 负责网络和数据模型。

应当形成的简历亮点：

- Muduo Reactor 网络模型与多线程连接处理。
- 基于状态机的复杂牌局规则，以及全押边池和奇数筹码算法。
- “每个房间单线程串行执行”的房间 Actor 模型，避免大量共享锁。
- TCP 粘包/半包处理、心跳、序列号、幂等请求、断线重连和状态快照。
- MySQL 事务结算、虚拟筹码账本、历史牌局和操作记录。
- Redis 节点注册、在线状态、房间路由和非关键通知。
- 多实例下的房间单节点归属，避免同一牌局被多个节点共同写入。
- 自动化规则测试、协议模糊测试、Sanitizer、并发压测和故障测试。

第一版不堆叠 Kubernetes、Kafka 或复杂微服务。完整性、可解释性和可验证性优先于技术名词数量。

- 39～45：必须学习并亲手完成一次负载均衡、跨服务器通信、Nginx、Redis Pub/Sub、CMake 和 Git 实验。
- 46：整理原教程项目的已知问题。
- 47：安全传输、历史存储、消息顺序、可靠传输、Redis 故障和客户端状态感知全部学习；简历课程在项目完成后再看。

Redis Pub/Sub 是至多一次投递，只能承载房间列表刷新、在线状态等允许丢失的通知，不能承载下注和结算。参考 [Redis Pub/Sub 官方说明](https://redis.io/docs/latest/develop/pubsub/)。

额外需要学习：

- C++17：RAII、智能指针、移动语义、线程安全、原子变量、条件变量和生命周期管理。
- 网络：TCP 字节流、粘包半包、长度字段协议、心跳、超时、背压、重连和 TLS。
- Muduo：`EventLoop`、`TcpConnection`、线程池、回调生命周期和跨线程任务投递。
- 数据库：索引、事务、隔离级别、预处理语句、连接池和幂等写入。
- Redis：TTL、Pub/Sub、Streams、故障降级，以及缓存数据和事实数据的边界。
- 德州扑克：按钮位、大小盲、行动顺序、最小加注、全押、边池、平局和奇数筹码。
- 工程质量：自动测试、ASan/UBSan/TSan、日志、指标、压测和故障注入。
- Qt：信号槽、`QTcpSocket`/`QSslSocket`、Model/View、QML 状态与动画、网络线程和 UI 线程隔离。参考 [Qt Model/View 文档](https://doc.qt.io/qt-6/model-view-programming.html)。

## 3. 核心架构和接口

服务端分层：

- `net`：Muduo 连接、长度字段解码、心跳、发送队列和限流。
- `protocol`：共享 Protobuf 消息和错误码。
- `application`：认证、会话、命令分发和房间管理。
- `domain`：纯 C++ 扑克状态机、牌型判断、下注和结算，不依赖网络和数据库。
- `storage`：MySQL 连接池、预处理语句、事务和迁移脚本。
- `cluster`：Redis 节点心跳、房间归属、临时加入凭证和大厅通知。
- `observability`：结构化日志、健康检查和指标。

网络协议：

- 四字节大端长度前缀加 Protobuf `Envelope`。
- `Envelope` 固定包含 `protocol_version`、`request_id`、`client_sequence`、`message_type` 和具体消息体。
- 服务端事件包含 `table_id`、`hand_id` 和 `server_sequence`。
- 重复 `request_id` 不得造成二次下注、二次买入或二次结算。
- 单包设定大小上限；非法、未知和越权消息返回统一错误并记录日志。

公共业务消息：

- 认证：注册、登录、登出、刷新会话。
- 大厅：创建房间、列出房间、加入房间、离开房间。
- 牌桌：入座、准备、行动、获取快照和重连。
- 行动：弃牌、过牌、跟注、下注、加注和全押。
- 事件：牌局阶段、行动玩家、筹码变化、公共牌、结算和房间关闭。

## 4. 并发、安全与一致性

- 网络 I/O 线程只负责收发和解码，不直接执行数据库操作。
- 房间按 `table_id` 分配到固定逻辑执行器，同一房间的命令始终串行处理。
- 不允许两个线程同时修改同一牌桌状态。
- MySQL 是用户、筹码账本和历史牌局的事实来源。
- 结算使用事务和唯一业务键，保证同一手牌只能结算一次。
- 密码使用 Argon2id，SQL 使用预处理语句；源码中不得保存数据库明文口令。
- 洗牌使用安全随机数和 Fisher–Yates，并允许测试注入固定随机源。
- 内存状态发生关键变化后，动作或结算成功持久化之前不向客户端确认最终成功。

## 5. 多实例扩展

单实例验收后增加：

- 大厅节点负责登录、房间查询和游戏节点选择。
- 游戏节点定期向 Redis 写入带 TTL 的节点心跳和负载。
- 创建房间时选择负载较低的游戏节点，并记录 `room_id -> node_id`。
- 客户端取得短期一次性加入凭证后，直接连接房间所属游戏节点。
- 一局牌始终由一个游戏节点权威执行，不通过 Redis Pub/Sub 转发下注。
- 节点宕机后停止给它分配新房间；第一版不实时迁移进行中的牌局，而是中止并根据持久化快照安全退回筹码。

## 6. 原始 20 周安排

- 第 1 周：看完剩余教程，运行聊天服务器集群实验；为教程版本建立基线标签。
- 第 2～3 周：学习 TCP、Muduo、C++ 并发、MySQL 事务和 Redis 语义；完成长度字段解码器与线程安全队列练习。
- 第 4～5 周：重构目录和 CMake；引入 Protobuf、配置、连接池、日志、数据库迁移、认证和会话。
- 第 6～9 周：实现纯领域牌局引擎，包括牌堆、牌型、行动合法性、下注阶段、全押边池和结算。
- 第 10～12 周：接入网络层，实现房间、座位、超时、个性化消息、断线重连、快照和幂等。
- 第 13～14 周：实现用户、虚拟筹码账本、牌局历史、安全机制和异常结算恢复。
- 第 15 周：完成单元测试、集成测试、Sanitizer 和协议模糊测试。
- 第 16 周：实现机器人压测客户端、指标、Docker Compose、云服务器部署和首版演示。
- 第 17 周：增加 Redis 节点注册、房间归属和双游戏节点演示。
- 第 18～20 周：学习 Qt Quick/QML，完成登录、大厅、牌桌、操作区、重连提示和结算界面；视觉精修后置。

默认每周投入不少于 25 小时。实际节奏可以变慢，但验收顺序不变。

## 7. 测试与最终验收

必须通过：

- 穷举全部 2,598,960 种五张牌组合，分类数量与标准结果一致。
- 覆盖多人全押、多级边池、平分底池、奇数筹码、最小加注和大小盲特殊顺序。
- 属性测试保证牌不重复、筹码总量守恒、非当前玩家不能行动、一手牌只能结算一次。
- 模拟 TCP 拆包、粘包、超大包、畸形 Protobuf、重复请求和乱序业务序列。
- 模拟掉线重连、超时、Redis 不可用、MySQL 短暂不可用和游戏节点退出。
- 领域核心代码行覆盖率不低于 85%。
- 固定 2 核 4 GB Ubuntu 环境：至少 5,000 条连接、500 个活跃房间运行 30 分钟；无错误结算，服务端操作响应 p99 不高于 100 ms，并保存 CPU、内存和吞吐量。
- 两个游戏节点可以分配不同房间；停止一个节点后，新房间只进入健康节点。

最终仓库必须包含：

- 架构图、状态机图、协议说明、数据库设计和一致性说明。
- 一条命令启动的开发环境和数据库迁移。
- GitHub Actions 构建与测试。
- 可复现的压测方法和真实结果；简历中不填写未经验证的数据。
- 2～3 分钟演示视频：多人连接、完整牌局、全押边池、断线重连、双节点分配和监控指标。

面试重点：

- 为什么房间要串行化？
- 为什么下注不能使用 Redis Pub/Sub？
- 如何解决 TCP 粘包和半包？
- 如何避免重复买入和重复结算？
- 节点宕机后如何保护玩家的虚拟筹码？
